# OA-06 Reproducible Two-Node Demo and Documentation

## Intent

OA-06 replaces the OA-00 failure sentinel `scripts/demo.sh` with a
reproducible two-node Option A demonstration and completes the README
documentation. The demo drives two fully independent node runtimes (A and B)
exclusively through the frozen OA-05 CLI, proves the A3-A8 properties with
public-ID/count-only observations, and never fabricates a capability Option A
does not have.

The package adds no Rust library or binary code, no dependency, no feature,
and no manifest change: `Cargo.toml` and `Cargo.lock` stay byte-identical to
the OA-05 state 6347a10. Deliverables are the bash harness, one Rust test
file, one verifier, README sections, predecessor-verifier guard updates, and
this spec.

## Recorded decisions

### No dependency delta

OA-06 needs only bash, coreutils, `ps`, `python3 -I`, `git` (tests only),
`cargo`, and the two workspace binaries. The frozen D-04-01 record is not
amended; verify-oa06.sh asserts the manifest is unchanged from 6347a10 by
`git diff --exit-code` over `Cargo.toml` and `Cargo.lock`.

### Runtime root and cleanup policy

The demo creates a private 0700 temporary runtime root (fresh per run). An
explicit override `OA06_DEMO_RUNTIME_ROOT` may name an absent or empty
directory so tests can observe cleanup; the demo creates it with 0700 and
chmods any pre-existing empty directory to 0700, rejecting a non-empty or
non-directory target, so secrets always sit inside a private root. On
success the whole runtime root is deleted unless `OA06_DEMO_KEEP=1` requests
debug retention (then the path is printed). On failure the runtime root and
its logs are preserved and the path is printed; secrets stay inside the
private root in both cases. Secrets are always freshly generated by
`contextmesh key generate` / `contextmesh token generate` (OS entropy);
checked-in fixture secrets are never used or accepted by the demo.

### Test-only fault injection

The harness accepts environment hooks that are absent in normal runs,
documented here and in the README as test-only, and cannot make a broken
system pass:

- `OA06_DEMO_READY_TIMEOUT_SECS` (default 15, minimum 1): hard bound for
  daemon readiness polling per start.
- `OA06_DEMO_TEST_SERVE_DELAY_SECS`: delay before a serve process is
  exec'd, delivered by a wrapper that traps TERM and kills its sleep child so
  no orphan process survives cleanup. Used to prove bounded readiness
  polling without blind sleeps.
- `OA06_DEMO_TEST_CRASH_AFTER_READY=node-a|node-b`: kills that recorded
  daemon with KILL immediately after both nodes are ready, proving failure
  detection, bounded cleanup of the surviving daemon, and log preservation.

Injection hooks only remove or delay work; they never bypass an assertion.

### Stage-set and test-matrix deltas from the plan letter

- Stage 2 additionally exercises the frozen `key repair-permissions`
  subcommand as a no-op repair of an already-0600 file. This strengthens
  command coverage and changes no stage semantics.
- Plan section 31's "occupy port" injection is structurally impossible:
  daemons bind `127.0.0.1:0` and every peer URL comes from the ready file,
  so no fixed port can be occupied. The equivalent adversarial condition —
  concurrent independent demo instances competing for ephemeral ports — is
  tested instead and disclosed as a substitution.
- Concurrent demo instances each run `cargo build --workspace --locked` in
  stage 1; cargo serializes them on the target-directory lock, which is
  accepted behavior, not a failure mode.


### Count-only observability

All assertions parse either the CLI's single canonical JSON document or
frozen on-disk artifacts (the exported bundle file, the ready file, file
metadata) with `python3 -I`, comparing only public identifiers, counts, and
booleans. The demo never depends on prose, byte offsets, or ambiguous grep
matches, and never prints key, token, or seed material.

## Harness contract

1. `set -euo pipefail`; private temporary runtime root; EXIT/INT/TERM trap.
2. Independent per-node files: `node-a.db`, `node-b.db`, `node-a.key`,
   `node-b.key`, `node-a.token`, `node-b.token`, `node-a.log`, `node-b.log`,
   `node-a.ready` (`node-a-2.ready` after restart), and PID records.
3. Daemons run `contextmesh serve --listen 127.0.0.1:0` and publish
   readiness atomically through the frozen CLI ready-file mechanism after
   bind; the harness polls the ready file with a hard timeout and a
   liveness check (`kill -0`) and never sleeps blindly.
4. Cleanup sends TERM to exactly the recorded child PIDs, waits a bounded
   grace, then KILLs and reaps. No other process is signaled.
5. Failure preserves logs and prints the runtime path; success deletes the
   runtime root unless `OA06_DEMO_KEEP=1`.
6. JSON is parsed only with isolated `python3 -I` one-liners.
7. Output is stable `stage NN ...` lines plus a final `demo: PASS ...` or
   `demo: FAIL ...` line, containing only public IDs and counts.

## Seventeen-stage demo

| Stage | Commands | Assertions |
|---:|---|---|
| 1 | `cargo build --workspace --locked` | `target/debug/contextmesh` and `target/debug/demo_agent` exist and are executable |
| 2 | `key generate` x2, `token generate` x2, `key repair-permissions` | distinct authors; key/token files exist with mode 0600 |
| 3 | `context create` (A), `context authorize` (A adds B) | context/genesis/branch returned; empty authorize result |
| 4 | `bundle export` (A, head=genesis), `context join` (B) | descriptor has exactly one zero-parent `context.genesis` event; B joins from the descriptor's own context/genesis IDs with authors A and B |
| 5 | `serve` x2 on `127.0.0.1:0` | both ready files publish distinct addresses; optional crash injection |
| 6 | `sync` (B from A), `show refs` (B local) | inserted=1, pages>=1, remote refs updated=1; B local refs=0 (no implicit local movement) |
| 7 | `branch create` (B main from genesis) | branch main; B local refs=1 |
| 8 | `invoke` (A, distinct input), `invocation pending`, `invocation detached`, `show event` | outcome=response; pending=0; detached=0; result head kind `agent.response`; A local refs=1 |
| 9 | `invoke` (B, distinct input), `invocation pending`, `invocation detached` | outcome=response; pending=0; detached=0; distinct event IDs from stage 8; B local refs=1 |
| 10 | `sync` (B from A), `sync` (A from B), `show refs` local+peer both | each direction inserted=2; A local refs=1 and B local refs=1 unchanged; each side holds exactly one namespaced peer ref |
| 11 | `branch create` (A merged), `merge` (A, parents A main + peer B main) | merge event returned; A local refs=2 |
| 12 | `sync` (B from A), `show projection` (A and B over merge head) | B inserted=1; both projections count the same total and each ancestor exactly once (6 events) |
| 13 | TERM both daemons, restart both | old PIDs dead before restart; new ready files publish new ephemeral ports on the same databases |
| 14 | `verify` (A and B), `show projection` both | valid=true both; projection counts still equal |
| 15 | `sync` (A from B), `sync` (B from A), `show refs` both | inserted=0 both; local ref counts unchanged (A=2, B=1) |
| 16 | `bundle export` (B), mutate one signature byte, `bundle import` (A) | import exits non-zero with ok=false; A verify still valid=true; A local refs=2; merge projection still 6 |
| 17 | — | prints `demo: PASS` with public context ID, author count, event counts, ref counts, stage count; no secrets |

   CLI-unobservable: `show projection` emits only an event count, so the
   strongest available equality assertion is equal counts (6) on both nodes
   over the same merge head, backed by `verify` integrity on both sides;
   full sequence equality is asserted only through the recorded six event
   IDs each node admits.

The demo never issues synchronized requests, never promotes a remote ref,
never repairs corruption, and never exposes a non-loopback listener.

## Change control and boundary

Changing the frozen stage set or their assertions, weakening cleanup or
secrecy rules, adding dependencies or non-loopback listeners to the demo,
executing synchronized requests, promoting remote refs, repairing corruption
in the demo, or claiming capabilities Option A does not have requires
explicit review and normally new approval. Option B remains blocked until
OA-07 records Option A complete with direct A1-A8 evidence.
